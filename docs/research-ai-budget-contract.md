## 2. Deterministic preparation — B1

Propose a synchronous bounded library operation, not a worker or autonomous agent. A case is a predeclared synthetic review question within one task/context. Its inputs must originate independently of private project facts; selecting or rewriting synthetic examples from private observations would itself disclose information and is excluded.

1. **Qualify before reading.** Resolve trusted project/context ownership, active generation, exact data decisions and current source availability. Apply [context isolation](research-subject-context.md#3-生命周期隔离与事务) and [observation lifecycle](research-observation-intake.md#4-生命周期与操作责任); close/transfer/hold/delete/quarantine/revoke, missing recovery qualification or unavailable provenance stops consumption. Local facts may restrict local eligibility through existing qualified services; they never enter model context, including as hashes, summaries, counts or synthetic-looking gaps.
2. **Rules first.** Evaluate only the versioned local policy and explicitly selected, currently eligible exact rules. If they satisfy the requested explanation/prioritization, return `RULES_SUFFICIENT`, with references and fixed templates, zero provider calls. Missing facts, independent expectations, mapping or session evidence returns `NEEDS_INPUT`; unsupported shape returns `UNSUPPORTED`. A model cannot repair either condition.
3. **One bounded retrieval.** If an explanation/priority remains unresolved, query only the eligible independent `synthetic_authored` / `reusable_synthetic` mechanism/rule catalog. Before ranking, validate exact versions, contamination ancestry, review/reuse, real RA-03/W3 validation and separate publication, plus independently approved egress projections. No project cards, external triage, standalone counterexample-card admission, test-only publication, implicit latest or global private search. Existing [RA-03 ranking and bounds](research-knowledge-retrieval.md#3-查询限额与结果) are ceilings, not new permissions: keywords ≤8 ×32 ASCII, tags ≤8, selected refs ≤32, scan ≤256 (257 refuses), qualified results ≤8. Propose top-k **4**, retaining the existing score and tie-break order; no embeddings, model query rewriting or second search. Oversized/partially qualified results fail as a whole.
4. **Decide necessity.** A sufficient retrieved explanation returns `RETRIEVAL_SUFFICIENT`. No eligible match returns `NO_ELIGIBLE_RULE`, not an invitation to invent a rule. Escalate only for a predeclared review-priority question with at least two eligible candidate/rule pairs, where the versioned deterministic policy explicitly returns `PRIORITY_UNRESOLVED`, and current model/data/account/budget approvals permit that finite question. Retrieval rank alone is not uncertainty or model necessity. Record the bounded reason code and policy version locally. Missing approval returns `AWAITING_APPROVAL`; any bound failure returns `LIMIT_EXCEEDED`.
5. **Construct once, then reserve.** Use ≤8 independently reviewed synthetic candidates, ≤4 complete approved claim projections (each ≤512 UTF-8 bytes) and ≤8 synthetic gaps, with W1's exact schema/byte/depth/node caps. Do not truncate a card or drop its limitations to fit. An approved projection needs its own exact digest and egress decision. Issue fresh per-call opaque handles, reject aliases/duplicates, and bind exact source/decision/version/digest, allowed pairs, project/context generation, policy/retrieval/prompt/schema/profile versions and earliest expiry. No raw source copy or conversation history. A second call requires a distinct predeclared question and a new qualification/reservation; refusal, failure, missing usage or an unsolved first question never triggers retry/rephrasing.

The necessity policy is a finite reviewed table keyed by trusted question kind and exact rule/template versions. Each entry chooses a complete fixed template, an enumerated missing-input set, an explicit priority-review question with allowed pairs, or unsupported; an absent entry is unsupported. Only the priority-review entry can yield `PRIORITY_UNRESOLVED`, after the other qualifications above. Text content, retrieval-score ties and model feedback cannot create table entries. The concrete table and its coverage require B1 review before implementation.

Requalify after retrieval, after context rendering, after admission/rate waiting, before secret resolution and first write, and before consuming/encoding either suggestions or refusal. Use **completed-lookup** ordered monotonic/wall time and cancellation at each boundary; expiry equality rejects. Untrusted text stays data and cannot modify the fixed prompt, policy or permission. Fixed preparation statuses are proposed local W2 outputs, not additions to W1's model or error schemas.

**Current integration gap:** RA-03's query API also performs subject/fact qualification and may return project-local material; its full response is not provider input. RA-03/W3 added conditional publication after the historical W2 closed gate ([current publication behavior](research-rule-validation.md#2-不可变证据与发布资格)). Recommend a separately reviewed internal retrieval/projection seam reusing those eligibility checks and ordering, with pre-ranking scope restrictions; do not bypass the existing checks or silently implement it. W1 accepts a synthetic catalog binding but does not implement that catalog, preparation policy or decision issuer. These are B1 dependencies, not permissions inferred from empty/matching query results.

## 3. Receipt, ownership and W1 interfaces — B2/B8

Proposed logical contract `ra-ai-budget/1`; no table, migration or public API is created here. Unknown versions, extra fields and coercion reject. Opaque local identifiers are 1–64 ASCII `[A-Za-z0-9_-]`, digests 64 lowercase hex, counters strict nonnegative int ≤`2^63−1` with checked arithmetic, generations positive int ≤`2147483647`. Timestamps are trusted aware UTC, canonically six fractional digits, with half-open validity; caller clocks cannot renew authority. Unknown required caps remain null and prohibit admission; explicit zero prohibits spending, not unlimited use.

## 4. Atomic boundaries and recovery — B3/B4/B6

**Storage recommendation, not adoption:** assess PostgreSQL as the reservation/settlement authority, with unique keys and short transactions, plus an independently durable send observer. An in-memory implementation is useful only for fake tests. Two PostgreSQL tables updated by the same callback are not independent evidence of real events.

Proposed final-send protocol:

1. Atomically lock account then task budget rows in stable ID order; check all token/cost/call-count limits, unresolved holds, policy versions and deadlines; create the reservation and append its event together. Check sums, not a stale cached balance. Failed transactions grant no receipt. Admission/rate waiting, preparation, secret resolution, DNS and TLS run without a database transaction or final-send mutex held.
2. At `sending`, acquire a **coarse provider-send/lifecycle guard G**, bounded by the remaining call deadline. Proposed implementation: a dedicated PostgreSQL **session advisory lock**, with every relevant lifecycle/config/account-cancel writer acquiring the same guard *before* its existing locks. Under G, re-read authority and ownership in short transactions, checking fresh time/cancellation after waiting and reading. Commit `SEND_INTENT` durably; uncertain commit acknowledgement means no write and reconciliation, not a repeated commit/send attempt.
3. Obtain durable acknowledgement from the independent observer for the exact one-use send permit. Then requalify inside G, including W1's `write_ready` boundary. The trusted transport consumes that permit at its actual first-write boundary and reports bounded send/close observations. No SQL transaction spans that write. G covers only final checks/marking/local observer work and the bounded first write (proposed ≤min(3s, remaining deadline)); release it before any response wait. Local observer work has a remaining-deadline bound too. Failure after marking remains in doubt until independently resolved.
4. Capture final usage independently of proposal validity, end the transport, and post a bounded observation. In a short account→task→call transaction, verify binding/event/generation/currency/rate, append the observation/settlement and update both budget projections atomically. Result omission cannot erase this event. Release admission only when the sender cannot continue; unknown usage still blocks new account/task calls. No long transaction spans response reads or operator recovery.

G is a **new coordination proposal**, not an existing guarantee. Current context/knowledge/table locks do not automatically participate, and merely using a new advisory key would leave a race. Every relevant close/transfer/source/review/publication/hold/delete/config/key-version/cancellation path must be inventoried, ordered and tested; no writer may acquire G while holding locks needed by its holder. Such integration changes require separate implementation review. A coarse guard trades throughput for an auditable lock order; deployment/account concurrency remains one.

PostgreSQL session advisory locks survive transaction rollback and require application cooperation; row/transaction locks end with their transaction. That supports the proposed separation of commit and guarded first write, but does not prove the entire protocol. [PostgreSQL 16 locking](https://www.postgresql.org/docs/16/explicit-locking.html#ADVISORY-LOCKS), accessed 2026-09-11. Durable acknowledgement also requires a reviewed WAL/storage/failover configuration; asynchronous commit can acknowledge before durable WAL. [PostgreSQL 16 WAL settings](https://www.postgresql.org/docs/16/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT), accessed 2026-09-11. No database configuration is changed here.

**Fencing limitation:** a database generation or expired lease alone cannot stop a paused process from later writing an already-open socket. G lost on connection failure is not proof that sender is dead. Recommend no automatic takeover of `ADMITTED` or later calls: fence the old transport/permit and prove termination before freeing the concurrency slot. A resumed stale owner must be rejected at the write boundary, not merely when persisting its result. Leases identify ownership and never extend call/source/budget deadlines. Until fencing and failure-atomic observer behavior are demonstrated, live calls remain disabled; no distributed exactly-once send is claimed.

| Crash/cancellation point | Recovery proposal; never automatic replay |
| --- | --- |
| Before reserve commit | No acknowledged reservation; inspect ambiguous commit by unique ID. Never allocate another ID to hide ambiguity. |
| Reserved, before admission/marker | Requalify policy and prove no permit/send/old sender survives; then close zero or explicitly authorize a new call. Elapsed leases do not themselves prove zero. |
| Marker committed, before first byte | Conservative in-doubt, even if the application believes it sent nothing. Independent permit revocation/closed-stream evidence may establish zero; otherwise keep reserve. |
| First write/response/record/settlement interrupted | Preserve marker and independent observations; known final usage can settle without a display. Missing or partial final usage stays unknown. A stale owner's genuine usage may be appended by recovery under a new owner; it cannot overwrite state, return stale display or clear that owner's claim. |
| Cancellation wins G before marker | Deny send; fence/close permit, record proven zero if supported. Cancellation occurring inside an authority lookup is checked on completion. |
| Send wins G before cancellation | Do not claim withdrawal of bytes or charges. Stop further work, close transport, preserve known usage or unresolved reserve, and suppress suggestions/refusal consumption. No restart of a cancelled task version. |
| Delayed usage / duplicate / conflicting receipt | Same event ID and identical binding/content is an idempotent read of its prior settlement. Same ID with different content, or incompatible final totals, appends conflict evidence and freezes admission; a human-approved correction posts an explicit delta, never overwrites or double charges both totals. |

Operator recovery is a finite, explicit procedure: pause task/account and relevant egress; establish the old sender/permit cannot act; inventory reservation/result/observer/provider evidence for the account window; correlate exact IDs/versions; record zero, final usage or unresolved/conflict with a recovery decision; atomically settle only proven amounts. Resume requires current data/config/budget qualification and a separate decision for eligible new work. Restart, backup restore or account-period rollover never clears unknown liability. Persist elapsed-time charges/holds and absolute expiries; monotonic values from different process epochs cannot be compared or reset into a fresh allowance. Unreconstructable elapsed time blocks admission. RA-06 CLI/worker scheduling is outside this proposal.

**Both ledgers can omit the same event.** Require an observation channel at the only permitted byte-writing boundary, with its own durable sequence/high-water marks and separately retained acknowledgements outside the result/budget failure domain. Recovery must compare those records against account-specific provider request/usage evidence where available, including delayed reporting and other account consumers. Network byte counters prove neither model completion nor cost; an aggregate bill may expose a discrepancy without identifying a call. Exclusive account use and enforced non-bypassable egress are evidence requirements, not established facts. A hash chain copied with both ledgers proves no completeness by itself. If all local channels share a failure, or provider evidence cannot attribute an event, the gap remains unbounded/unresolved: freeze the account, retain known reserves and display the coverage deficit. Ledger agreement alone never releases funds or proves hard caps. Do not automatically query a paid/API endpoint to fill the gap; the evidence channel, retention and any extra endpoint require separate approval.

## 5. Conservation, examples and feasibility — B5/B7

Use the adopted [§6 mapping/rate snapshot](research-ai-provider-contract.md#6-usage预算与未来-w2-接口-p), not a new price recommendation: `I=input_tokens`, `O=output_tokens` including reasoning, `C=cached_tokens`, `W=cache_write_tokens`, optional `R=reasoning_tokens`. Require strict integer counts, `C+W≤I`, `R≤O` when known and `total=I+O`. Ordinary input is `I−C−W`; reasoning/cache subsets are not added again. Missing required final fields are unknown, malformed fields invalid; neither is zero. No clamping of over-cap actuals.

In microusd, with upward rounding **once per call**:

`cost = ceil(2×(I−C−W) + 0.2×C + 2.5×W + 12×O)`

`r_tokens = 4096+1024 = 5120`; `r_cost = ceil(4096×2.5+1024×12) = 22528`.

For each token/cost dimension and **each** task/account budget: `H = B − S − U`, where B is the approved cap, S is settled actual usage, U is outstanding liability, and H is signed headroom. Admission requires active qualification, no unknown/conflict pause, sufficient call/time slots and `S+U+r≤B` in both dimensions. One call contributes once to its task and once to its account aggregate; those views are not added together as global spend. Outstanding liability is at least the original reserve, or a greater independently known lower bound; partial usage does not reduce it. A coverage gap means no proven upper bound, even if a numeric reserve remains.

On a qualified final amount `a`, atomically remove that call's held liability and add `a` to S. For a call whose held amount is r: `a + refund = r + overrun`, `refund=max(r−a,0)`, `overrun=max(a−r,0)`. Overrun remains visible; H may be negative and admission stops. If held liability had increased, use that larger held amount in the same equation. Identical duplicate settlement changes S/U/H by zero. Unresolved final cost keeps its entire cost reserve even if a token subtotal is known; record the subtotal separately, not twice as spend plus reserve.
